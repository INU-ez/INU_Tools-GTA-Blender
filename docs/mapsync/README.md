# Схемы системы связей IDE / IPL / IMG

Схемы описывают Blender-версию (`INU_tools/`, ветка `main`). Сверены с кодом 28.09.2026.
Различия версии для 3ds Max — в `docs/BLENDER_VS_MAX.md` репозитория Max.

## Как открыть

VS Code → расширение **Draw.io Integration** (`hediet.vscode-drawio`) → открыть `.drawio`-файл.

| Вкладка в [data-model.drawio](data-model.drawio) | Что показывает |
|---|---|
| **0 Игра и аддон** | Папка игры (gta.dat, IPL, IDE, IMG) слева, аддон справа, между ними все действия: кто что читает и пишет. Номер в кружке — вкладка с разбором |
| **1 Импорт** | Как строки IPL / IDE / записи IMG становятся объектами и что аддон запоминает |
| **2 IPL: Add новой** · **3 … после сдвига** · **4 … копии** | Файл IPL до и после Add: куда встают новые строки, как переписывается строка на месте, своя LOD-строка у копии |
| **5 IPL: Del** · **6 IPL: Del только LOD** | Удаление строк и **пересчёт колонки LOD** у всех строк; старые номера в памяти соседей |
| **7 IPL: правка снаружи** | Файл поправили в Блокноте / MEd: связь едет за строкой или снимается; опасная правка номеров LOD |
| **8 IPL: Sync, ▶, Check** | Чем отличаются три кнопки «из файла в Blender» на одном примере |
| **9 IDE: Add** · **10 IDE: смена ID** · **11 IDE: Del** | Строки IDE: на месте / перед end, перенумерация при смене ID, конфликт, удаление |
| **12 IMG: Export, 🗑, пересборка** | Каталог и сектора архива до и после: запись на месте, в конец, мёртвое место, пересборка |
| **13 Что если…** | Все опасные случаи, найденные прогоном кода аддона на тестовых файлах (IPL Add, IPL Del / наблюдатель / Sync, IDE, IMG). Подробно — `dev/diagrams/facts/scenarios_*.md` |
| **Add в IPL** | Дерево «да / нет»: что делает аддон, когда нажали Add в боксе IPL — какую строку обновит или добавит, откуда возьмёт LOD |
| **Файл изменили снаружи** | Дерево «да / нет»: что аддон делает сам, когда IPL или IDE изменили в другой программе — связь остаётся, переезжает или снимается |
| **Что где лежит** | Колонки IPL и IDE, записи IMG и откуда в Blender берётся каждое значение (одинаковый цвет — одно значение) |

Схема собирается скриптом — см. [dev/diagrams](../../dev/diagrams/README.md) (там же факты из кода и правила оформления).
Вкладки 1–12 рисуют файлы ровно такими, какими их делает код аддона: пример-проект прогоняется через настоящие `core/mapsync` и `core/img` (`dev/diagrams/scenario.py`).

## Как читать схему

- Деревья читаются сверху вниз: ромб — вопрос, из него две стрелки **да** / **нет**. Голубой ромб — к нему пришли по «да», красный — по «нет».
- Цвет итога: зелёный — всё в порядке, жёлтый — сработало с предупреждением, красный — связь снята или ошибка, белый — действие аддона.
- Вкладка **Что где лежит**: IPL и IDE нарисованы как в файле, пример — модель `myhouse` и её LOD `LODmyhouse`.
- Вкладки **1–12**: слева файл игры «Было» и «Стало» — одна строка таблицы = одна строка файла. `стр.` — номер строки в файле, `№` — номер строки inst, на который ссылается колонка LOD. Зелёная строка — новая, жёлтая — переписана (жирным — что изменилось), красная зачёркнутая — удалена, белая — не тронута. Красные стрелки — куда указывает колонка LOD. Справа — что нажали, шаги аддона (кружки с теми же номерами стоят у строк слева) и что аддон запомнил на объекте.

## Для разработчика: хрупкие места в коде

Подробности к красному блоку схемы и другие хрупкие места, сверенные с кодом.

Пути — относительно `INU_tools/`.

1. **Поиск строки в 2 м** (`RELINK_TOL`) берёт ближайшую свободную строку той же модели. Зарезервированы только строки других связанных объектов этого .blend (все сцены) и только при точном совпадении 0.01 — строки из других .blend не защищены. В `refresh_links` перепривязка жадная, в порядке объектов.
   `core/mapsync/ipl_doc.py:362-379, 346-353`, `ops/map_link.py:319-327, 726-741`
2. **`lod_index` в файле** — позиция среди inst-строк *этого* файла (вместе с нераспарсенными, без комментариев). Пересчитывается в `commit()` только для строк стиля SA. Импорт (`core/ipl._read_text_ipl`) битые строки пропускает — нумерация у импорта и у mapsync расходится.
   **VC / III:** колонки `lod_index` нет, после перечитывания строка модели теряет ссылку на LOD, и каждый повторный Add дописывает ещё одну LOD-строку; `remove()` свою LOD-строку не находит (проверено по коду, тестов VC/III в `dev/tests/test_mapsync.py` нет).
   `core/mapsync/ipl_doc.py:158-186, 386-405, 476-486`, `ops/map_link.py:449-477`, `core/ipl.py:806-808`
   28.09.2026 вечером в рабочей копии `ipl_doc.py` появилась (ещё не закоммичена) правка: для VC / III LOD-строка ищется по содержимому (`_lod_by_content`) — по прогону `probe_ipl_add.py` дубль LOD при повторном Add ушёл. После коммита — поправить этот пункт и ⚠-блок VC / III на вкладке «Add в IPL».
3. **`inu.lod_index`** — хранимый номер строки. Add его не читает (`commit()` считает заново), панель даёт его править, полный Export IPL берёт его запасным вариантом без пересчёта.
   `ops/map_link.py:236-237`, `core/mapsync/ipl_doc.py:485-486`, `ui/panels.py:3331`, `ops/ipl_export.py:114-137`
4. **LOD-партнёр:** `lod_object` принимается из любой сцены; если он пуст — LOD ищется по базе имени только в текущей сцене (из нескольких — имя без `.001`, затем по алфавиту). Кнопка «Поиск LOD» выбирает по другим правилам (с учётом регистра, первый найденный).
   `ops/map_link.py:86-108`, `ops/col_surface_ops.py:326-369`
5. **Оригинал или копия:** оригинал — объект с `obj.name == ipl_owner`. Если оригинал переименовать, выбор идёт по `session_uid`, который не сохраняется между сессиями; если оригинал удалить, единственная копия молча забирает его строку. Для копии панель пишет «добавится новым инстансом», а кнопка Add в этом боксе даёт ошибку «нет своего IPL».
   `ops/map_link.py:260-296`, `ui/panels.py:1204-1206`, `ops/ide_ipl.py:677-678`
6. **Add пишет в выбранный в панели файл**, даже если модель связана с другим: старая строка остаётся в прежнем файле (только предупреждение). Так же для IDE.
   `ops/map_link.py:415-429, 850-860`
7. **Файл пропал на момент проверки** (редактор сохраняет через удаление+переименование, сетевой диск) — наблюдатель снимает связи у *всех* объектов этого файла.
   `ops/map_watch.py:65-71`, `ops/map_link.py:716-737, 745-758`
8. **Имя LOD — три правила:** при Add — `ide_last_name`, иначе `'LOD'+база`; в полном Export IPL и в IMG — всегда `'LOD'+база`; в ID Manager — `'LOD'+clean`. У ванильных LOD вида `xyz_lod`, `tatar_str_1LOD` имена в IDE/IPL и в IMG расходятся. И две проверки «это LOD»: `is_lod_name` («lod» где угодно) и `_is_scene_lod_name` (строже).
   `ops/map_link.py:186-191`, `ops/ipl_export.py:57-59`, `ops/img_ops.py:1431, 2122, 2149`, `ops/id_manager_ops.py:116-121`, `core/ipl.py:674-696`, `core/model_classify.py:23-44`
9. **ID LOD:** если у LOD `model_id = 0`, в файл пишется id модели + 1, а сам LOD этот id не получает — панель сразу показывает «сменился ID». ID Manager выдаёт LOD независимый id; совпадение с +1 только предупреждает.
   `ops/map_link.py:194-199`, `ui/panels.py:1124-1126`, `ops/id_manager_ops.py:112-127`, `ops/ide_ipl.py:73-84`
10. **Конфликт ID в IDE** ищется только внутри целевого файла — тот же id в другом IDE игры не виден. Переименование через `ide_last_name` не проверяет, что новое имя уже есть под другим id.
    `core/mapsync/ide_doc.py:183-253`
11. **Бинарный IPL:** `lod_idx` указывает в одноимённый *текстовый* IPL; импорт из IMG не сдвигает `lod_index` бинарных строк, Map Import разрешает его в своём файле. mapsync бинарные файлы не редактирует. Строки IPL внутри IMG (текстовые и бинарные) не привязываются — Add ставит дубль в той же точке.
    `core/ipl.py:853-895`, `ops/img_ops.py:937-950`, `ops/map_ops.py:840-849`, `core/mapsync/ipl_doc.py:141-142, 376-379`
12. **Формат новых строк = игра сцены** (`gtatools_game`), а не файла: сцена VC → строка VC в SA-файле. Стиль существующей строки угадывается по числу колонок (13 → VC, даже если это SA+FLA).
    `ops/map_link.py:30-35, 436-437`, `core/mapsync/ipl_doc.py:71-81, 340-343`
13. **paths.json** перезаписывает `gtatools_ide_path` / `ipl_path` / `img_path` / `game_root` сцены при каждой загрузке .blend — «выбранный» файл для Add может прийти из другого проекта.
    `__init__.py:4429-4506, 5000-5002`
14. **IMG:** `img_target_file` ставят только импорт и Verify (Export to IMG — нет); Verify для LOD и COL ищет `база.dff` и находит DFF модели; одноимённые записи — ядро Blender берёт последнюю, игра — первую.
    `ops/img_ops.py:1294, 1504-1515`, `core/img.py:223-224`
15. **Файл и .blend не транзакционны:** операторы Add без UNDO — Ctrl+Z откатывает `obj.inu`, а файл остаётся; `.bak` — только при первой записи файла за сессию; запись в IMG идёт на месте, не атомарно.
    `ops/ide_ipl.py:206, 236`, `core/mapsync/textfile.py:97-139`, `core/img.py:448-575`
16. **IDE Sync from file и Check идут мимо core/mapsync:** Sync ищет сначала по имени, первый файл из gta.dat побеждает, `model_id` перезаписывается из файла; Check сверяет только id и снимает лишь `ide_linked`.
    `ops/ide_ipl.py:763-860, 928-958`
17. **`lod_ide_id / _name / _file`** только пишутся и показываются, не очищаются; Add их не читает (ищет LOD в IDE заново) — устаревает только подпись в панели.
    `ops/map_link.py:178-183, 464`, `ui/panels.py:3439-3445`
18. **Колонку LOD испортили руками** (удалили / вставили строку в Блокноте, номера не поправили): `IplDoc._parse` берёт `Row.lod = rows[orig_lod]` как есть, и `place()` переиспользует эту строку как LOD модели, если она не занята и на неё больше никто не ссылается. Проверено прогоном: следующий Add модели переписал **чужую ванильную строку** данными своего LOD, а настоящая LOD-строка осталась лишней. Защиты нет: не сверяется, что старая LOD-строка — действительно LOD этой модели (имя / ID / позиция).
    `core/mapsync/ipl_doc.py:180-186, 386-405`
19. **`inu.lod_index` у соседей устаревает после каждого Del**: пересчитываются номера в файле, а память других объектов — нет (наблюдатель при точном совпадении строки не перештамповывает). Видно в поле «LOD» и в полном Export IPL (уровень 2). Пример — вкладка 5.
    `ops/map_link.py:552-560, 726-731`, `ops/ipl_export.py:135-137`

## Как обновлять

При правке `ops/map_link.py`, `core/mapsync/*`, `ops/ide_ipl.py`, `ops/img_ops.py` или полей `obj.inu` — поправить схему и этот список в том же изменении.
